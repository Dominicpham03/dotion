## 1. Two clients, one UI

| | **Desktop app** | **Web UI** |
|---|---|---|
| Shell | Wails v2 (native window, WebView2 on Windows) | Any modern browser |
| Delivered as | Installer (`.exe`), later `.dmg` / AppImage | Served by the Go server from the same origin |
| UI code | `ui/` React app, `VITE_TARGET=desktop` | `ui/` React app, `VITE_TARGET=web` |
| Data source | **Local SQLite** through Go bindings | **Server API** over HTTPS |
| Offline | Full: read, write, search | Online-first; unsaved text kept in a local draft |
| Sync | Go engine in the app (outbox + pull) | None needed; every save goes straight to the server |
| Live updates | Go listens on SSE, emits a Wails event | Browser `EventSource` on `/v1/events` |
| Auth | None (Tailscale) or a token in the OS keychain | None (Tailscale) or an HttpOnly cookie |

The UI never knows which one it is running in. It talks to a `DiaryStore` interface, and the build chooses the implementation.

The desktop app is the heavier client because it owns an offline database and a sync engine, written in Go and sharing code with the server (`shared/`). The web client is deliberately thin.

## 3. The platform adapter

### 3.1 The interface

```ts
// ui/src/platform/types.ts
export type EntryId = string;

export interface Entry {
  id: EntryId;
  entryDate: string | null;        // "2026-10-05"
  title: string;
  body: JSONContent;               // TipTap / ProseMirror JSON
  version: number;
  updatedAt: string;
  deletedAt: string | null;
}

export interface EntrySummary {
  id: EntryId;
  entryDate: string | null;
  title: string;
  preview: string;                 // first ~140 characters of plain text
  updatedAt: string;
}

export type SaveResult =
  | { status: "saved"; entry: Entry }
  | { status: "queued"; entry: Entry }                    // desktop, offline
  | { status: "conflict"; current: Entry; copy: Entry };  // conflict copy already created

export type SyncStatus =
  | { state: "synced"; at: string }
  | { state: "syncing" }
  | { state: "offline"; pending: number }
  | { state: "error"; message: string };

export interface DiaryStore {
  getEntry(id: EntryId): Promise<Entry | null>;
  getEntryForDate(date: string): Promise<Entry | null>;
  listRange(from: string, to: string): Promise<EntrySummary[]>;
  listRecent(limit: number): Promise<EntrySummary[]>;
  search(query: string): Promise<SearchHit[]>;

  saveEntry(draft: EntryDraft, baseVersion: number): Promise<SaveResult>;
  deleteEntry(id: EntryId, baseVersion: number): Promise<void>;

  onChanged(cb: (ids: EntryId[] | "all") => void): () => void;  // returns unsubscribe
  onSyncStatus(cb: (s: SyncStatus) => void): () => void;
}
```

`saveEntry` already handles conflicts on both platforms and returns a `conflict` result with the copy it created. The UI only has to show it (see §9).


The alias means the desktop bundle contains no HTTP client code and the web bundle contains no Wails bindings.

### 3.3 HTTP adapter (web)

```ts
// ui/src/platform/http.ts
async function api<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`/v1${path}`, {
    ...init,
    credentials: "same-origin",
    headers: { "Content-Type": "application/json", "X-Diary-Client": "1", ...init.headers },
  });
  if (res.status === 401) throw new AuthRequired();
  const body = res.status === 204 ? null : await res.json();
  if (!res.ok) throw new ApiError(res.status, body.error, body);
  return body as T;
}

export const store: DiaryStore = {
  getEntry: (id) => api<Entry>(`/entries/${id}`).catch(nullOn404),

  async saveEntry(draft, baseVersion) {
    try {
      const entry = await api<Entry>(`/entries/${draft.id}`, {
        method: "PUT",
        headers: { "Idempotency-Key": uuidv7() },
        body: JSON.stringify({ base_version: baseVersion, entry_date: draft.entryDate, title: draft.title, body: draft.body }),
      });
      return { status: "saved", entry };
    } catch (e) {
      if (e instanceof ApiError && e.code === "conflict") {
        const copy = await createConflictCopy(draft);       // PUT new id, base_version 0
        return { status: "conflict", current: e.body.current, copy };
      }
      throw e;
    }
  },

  onChanged(cb) {
    const es = new EventSource("/v1/events");
    es.addEventListener("changed", () => cb("all"));
    return () => es.close();
  },
  // ...
};
```

The web client does not keep a cursor or call `/v1/sync`. When a notice arrives it simply refetches what is on screen through TanStack Query (§4).

### 3.4 Wails adapter (desktop)

```ts
// ui/src/platform/wails.ts
import * as App from "./wailsjs/go/main/App";          // generated from Go methods
import { EventsOn } from "./wailsjs/runtime/runtime";

export const store: DiaryStore = {
  getEntry: (id) => App.GetEntry(id),
  getEntryForDate: (d) => App.GetEntryForDate(d),
  saveEntry: (draft, base) => App.SaveEntry(draft, base),   // writes SQLite + outbox, returns immediately
  search: (q) => App.Search(q),                              // local FTS5, works offline
  onChanged: (cb) => EventsOn("entries:changed", (ids: string[]) => cb(ids)),
  onSyncStatus: (cb) => EventsOn("sync:status", cb),
  // ...
};
```

Every desktop call is a local SQLite operation that takes a few milliseconds and never waits on the network.

## 4. State and data flow

Both builds use **TanStack Query** on top of the adapter, so screens are written once.

| Query key | Loads |
|---|---|
| `["entry", id]` | one full entry |
| `["entry-date", "2026-10-05"]` | the entry for a day (or null) |
| `["range", from, to]` | summaries for the calendar month |
| `["recent"]` | sidebar list |
| `["search", q]` | search hits |

**Reacting to changes:**

```ts
useEffect(() => store.onChanged((ids) => {
  if (ids === "all") return queryClient.invalidateQueries();
  ids.forEach((id) => queryClient.invalidateQueries({ queryKey: ["entry", id] }));
  queryClient.invalidateQueries({ queryKey: ["range"] });
  queryClient.invalidateQueries({ queryKey: ["recent"] });
}), []);
```

**The open entry is special.** The editor holds the text the user is typing, so a refetch must not overwrite it blindly. The rule:

| Incoming version vs editor | Editor has unsaved changes? | Action |
|---|---|---|
| same version | any | nothing (it is our own save echoing back) |
| newer | no | replace the editor content, keep the scroll position, show "Updated from another device" for 3 s |
| newer | yes | keep typing; the next save returns a conflict and §9 takes over |

## 5. Screens and navigation

| Route | Screen | Purpose |
|---|---|---|
| `/` → `/today` | **Today** | Opens today's entry, or an empty editor with today's date as title. The entry is created on the first keystroke, not when the page opens, so empty days never produce empty entries. |
| `/day/:date` | **Day** | Same as Today for any date (from the calendar). |
| `/entry/:id` | **Entry** | Free notes without a date, and conflict copies. |
| `/calendar/:yyyy-mm?` | **Calendar** | Month grid; days with entries are marked; click opens the day. |
| `/search?q=` | **Search** | Results with highlighted snippets. Desktop searches local SQLite; web calls `/v1/search`. |
| `/settings` | **Settings** | Theme, editor font size; desktop also: server URL, sync status, "sync now", sign out. |
| `/welcome` | **First run** (desktop) | Enter the server URL, test the connection, sign in if needed. |
| `/login` | **Login** (web, password mode only) | Shown when the API returns 401. |

**Layout:** a left sidebar (Today, Calendar, Search, recent entries, sync badge) and the main pane. Below 720 px wide the sidebar collapses behind a menu button, which makes the web UI usable on a phone over Tailscale.

**Router:** `createBrowserRouter` on web (real URLs, the server's SPA fallback handles reloads); `createHashRouter` on desktop (no server paths inside the WebView).

- The **title** is a separate plain input above the editor. For daily entries it defaults to the weekday and date (for example "Monday, 5 October") and can be changed.
- Images and attachments are out of scope for v1 (see PLAN.md, open decisions).

### 6.2 Autosave

There is no Save button. Saving follows these rules:

1. **Debounce:** save 800 ms after the last keystroke.
2. **Flush:** also save immediately on blur, route change, window close (`beforeunload` on web, Wails `OnBeforeClose` on desktop) and every 10 s during continuous typing.
3. **One save in flight per entry.** If the user types while a save is running, mark the entry as "dirty again" and send one more save when the first returns, using the **new** version as `base_version`. Without this rule, two overlapping saves from the same device would conflict with each other.
4. **Track `baseVersion`** in the hook: it starts at the loaded entry's version (0 for new) and becomes the returned version after each successful save.

```ts
// ui/src/features/entry/useAutosave.ts (shape)
function useAutosave(entryId: string, initialVersion: number) {
  const base = useRef(initialVersion);
  const inFlight = useRef(false);
  const pending = useRef<EntryDraft | null>(null);

  const flush = useCallback(async () => {
    if (inFlight.current || !pending.current) return;
    const draft = pending.current; pending.current = null; inFlight.current = true;
    try {
      const r = await store.saveEntry(draft, base.current);
      if (r.status === "conflict") { base.current = r.current.version; showConflict(r); }
      else base.current = r.entry.version;
      clearLocalDraft(entryId);                       // web safety net, §7.2
    } catch (e) {
      pending.current ??= draft;                      // keep it for the next attempt
      reportSaveError(e);
    } finally {
      inFlight.current = false;
      if (pending.current) flush();                   // typed during the save
    }
  }, [entryId]);

  const schedule = useDebouncedCallback(flush, 800, { maxWait: 10_000 });
  return {
    onChange(draft: EntryDraft) { pending.current = draft; saveLocalDraft(draft); schedule(); },
    flush,
  };
}
```

A small status next to the title, wording kept literal:

|---|---|

## 7. Web client in depth

### 7.1 Online-first

Every read and write goes to the server. TanStack Query caches responses in memory for instant navigation, and `refetchOnWindowFocus` keeps a tab that sat in the background up to date.

### 7.2 Local draft safety net

The browser can lose network or close mid-sentence. To avoid losing text:

- Every editor change writes `{id, title, body, baseVersion, savedAt}` to `localStorage` under `draft:<id>`.
- A successful save removes it.
- When an entry opens and a draft exists that is newer than the server copy, a banner offers **Restore unsaved text** or **Discard**. Restoring saves it through the normal path, so a conflict is still detected if the server changed meanwhile.

This is not offline mode; it only protects the last few seconds of typing.

### 7.3 Live updates

`EventSource("/v1/events")` reconnects automatically (the server sends `retry: 3000`). On `changed`, the app invalidates its queries (§4). While disconnected, a thin bar says `Reconnecting…`, and saves still work through normal requests.

### 7.4 Auth

- **Tailscale mode:** nothing to do. Requests carry the identity automatically through the sidecar.
- **Password mode:** a 401 from any call redirects to `/login`. The cookie is HttpOnly, so the web code never sees or stores a token. All writes send `X-Diary-Client: 1` (CSRF guard, see BACKEND.md §10.2).

## 8. Desktop client in depth

The desktop app is a Go program (Wails) with the React UI in a native WebView. The Go side owns the local database and sync.

### 8.1 Go package layout

```
desktop/
├── main.go                  # wails.Run(...), embeds frontend/dist
├── app.go                   # App struct: methods exposed to the UI
├── internal/
│   ├── localdb/             # SQLite schema, queries, migrations
│   ├── outbox/              # enqueue, coalesce, take next, complete
│   ├── syncclient/          # push loop, pull loop, SSE listener, backoff
│   ├── api/                 # typed HTTP client for /v1 (uses shared/syncproto)
│   └── secrets/             # OS keychain via github.com/zalando/go-keyring
├── frontend/dist/           # written by `npm run build:desktop` (git-ignored)
└── wails.json
```

### 8.2 Local database

```sql
CREATE TABLE entries (
  id          TEXT PRIMARY KEY,
  entry_date  TEXT,
  title       TEXT NOT NULL DEFAULT '',
  body        TEXT NOT NULL,
  body_text   TEXT NOT NULL DEFAULT '',
  version     INTEGER NOT NULL,     -- last version confirmed by the server (0 = never synced)
  server_seq  INTEGER,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  deleted_at  TEXT
);
CREATE INDEX entries_date ON entries(entry_date) WHERE deleted_at IS NULL;

-- One pending change per entry. New edits replace the payload of the pending row.
CREATE TABLE outbox (
  entry_id      TEXT PRIMARY KEY,
  op            TEXT NOT NULL,      -- 'put' | 'delete'
  payload       TEXT NOT NULL,      -- JSON body for PUT
  base_version  INTEGER NOT NULL,   -- server version these edits started from
  rev           INTEGER NOT NULL,   -- bumped on every local edit
  idem_key      TEXT NOT NULL,      -- regenerated whenever rev changes
  attempts      INTEGER NOT NULL DEFAULT 0,
  next_try_at   TEXT,
  last_error    TEXT
);

CREATE TABLE sync_state (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- 'cursor' → "1843", 'server_url' → "https://diary.tailnet.ts.net", 'last_sync_at' → ...

CREATE VIRTUAL TABLE entries_fts USING fts5(title, body_text, content='entries', content_rowid='rowid');
-- plus the same three triggers as the server (BACKEND.md §7.2)
```

**Why one outbox row per entry:** typing produces many saves. Only the latest content matters, and it must be sent with the version the edits **started** from. Coalescing keeps the queue short (one request per changed entry after a long offline period) and keeps `base_version` correct.

### 8.3 Saving locally (`App.SaveEntry`)

In one SQLite transaction:

1. Upsert the entry row with the new title, body and `body_text` (`shared/prosemirror.ExtractText`). `version` is **not** changed; it stays the last server-confirmed version.
2. Upsert the outbox row:
   - no row yet → insert with `base_version = entries.version`, `rev = 1`, new `idem_key`;
   - row exists → replace `payload`, `rev = rev + 1`, new `idem_key`, keep `base_version`.
3. Commit, then nudge the sync engine (non-blocking channel send).

Return `{status: "queued"}` immediately. The sync engine later emits `entries:changed` when the server confirms.

### 8.4 The sync engine

A single goroutine runs this loop, so pushes and pulls never race each other:

```
         ┌──────────── triggers ─────────────┐
         │ local save nudge · SSE "changed"  │
         │ 60 s timer · app focus · network  │
         │ back · "Sync now" button          │
         └───────────────┬───────────────────┘
                         ▼
                 ┌──────────────┐   network error    ┌──────────┐
                 │  1. PUSH all │ ─────────────────► │ BACKOFF  │ 1s,2s,4s… max 60s
                 │  due outbox  │                    └────┬─────┘
                 └──────┬───────┘                         │ timer / trigger
                        ▼                                 │
                 ┌──────────────┐                         │
                 │  2. PULL     │ ◄───────────────────────┘
                 │  until done  │
                 └──────┬───────┘
                        ▼
                     IDLE (emit sync:status "synced")
```

**Push first, then pull.** Sending local edits before pulling means the pull's results already include them, and conflicts surface as clear 409s instead of ambiguous local merges.

#### Push, per outbox row

```
take row (entry_id, rev = R, base_version = B, idem_key = K)
PUT /v1/entries/{id}  base_version=B  Idempotency-Key=K
├─ 200 entry v(B+1)
│    tx: update entries.version = B+1, server_seq
│        if outbox.rev == R → delete row               (nothing typed since)
│        else              → set base_version = B+1     (keep newer edits queued)
├─ 409 current
│    tx: create conflict copy (new UUID) from this row's payload, queue it as a new outbox row (base 0)
│        overwrite local entry with `current`
│        delete the original outbox row
│    emit entries:changed [id, copyId], emit conflict:created {id, copyId}
├─ 404 (entry gone on server, base > 0)
│    re-queue as a create: base_version = 0
├─ 401 / 403   → stop, emit sync:status error "Sign in again", show Settings
├─ 4xx other   → mark row failed with last_error, skip it, keep going
└─ network/5xx → attempts++, next_try_at = backoff, go to BACKOFF
```

The `rev` check is what makes typing during a push safe: an edit made while the request was in flight stays queued and is sent next, based on the version the server just confirmed.

#### Pull

```
cursor = sync_state.cursor (0 on a fresh install)
loop:
  GET /v1/sync?since=cursor&limit=500
  tx:
    for each change:
      if an outbox row exists for change.id → skip   (our pending edit wins; push will settle it)
      else if change.deleted_at              → mark local row deleted (tombstone)
      else                                   → upsert local row with server content and version
    sync_state.cursor = response.cursor
  emit entries:changed [ids]
  until !has_more
```

Skipping entries with pending outbox rows is the key rule: the pull never overwrites text the user has not sent yet. If the server copy really moved on, the next push gets a 409 and the conflict path runs.

If the server answers `cursor_ahead` (restored from a backup), the engine sets `cursor = 0` and pulls everything again; outbox rows are untouched.

#### Live notices

A goroutine holds `GET /v1/events` open with a streaming HTTP client, parses `event: changed` lines, and sends a trigger to the loop. It reconnects with backoff. When it reconnects after a gap, it also triggers a pull, since notices may have been missed.

#### Status reporting

The engine emits `sync:status` on every state change: `syncing`, `synced` (with time), `offline` (with the pending count from the outbox), `error` (with a message). The sidebar badge and Settings page render it.

### 8.5 First run and settings

1. `/welcome` asks for the server URL (`https://diary.<tailnet>.ts.net`).
2. **Test connection** calls `/v1/health`, then `/v1/me`:
   - `200` → connected (Tailscale identity).
   - `401` in password mode → password field appears; `POST /v1/auth/login` returns a token stored with `go-keyring` (Windows Credential Manager).
   - network error → message: "Can't reach this address. Check that Tailscale is running on this computer."
3. On success: store the URL in `sync_state`, start the engine, perform the initial full pull with a progress bar (`n entries downloaded`).

Settings shows the URL, the signed-in login, last sync time, pending changes, **Sync now**, and **Disconnect** (stops syncing, keeps local data).

### 8.6 Window and lifecycle

- `OnBeforeClose`: ask the UI to flush autosave, then give the engine up to 3 s to push before exiting. Anything left stays in the outbox for next launch.
- `OnStartup`: open SQLite, run local migrations, start the engine.
- Single instance lock (`SingleInstanceLock` in Wails options) so two windows never share one database.
- Local data lives in `%APPDATA%\Diary\diary.db` on Windows.

## 9. Conflict experience

Conflicts should be rare (they need the same entry edited on two devices before either syncs) and must never lose text.

**What the user sees:**

```
┌──────────────────────────────────────────────────────────────────┐
│ ⚠  This entry was also edited on another device.                 │
│    Your version was saved as "Monday (conflict copy)".           │
│    [Compare side by side]   [Open my copy]   [Dismiss]           │
└──────────────────────────────────────────────────────────────────┘
```

- The open editor switches to the server version (the one other devices see).
- **Compare side by side** opens both versions read-only next to each other with a plain-text diff, so the user can copy what they need from their copy.
- The copy is a normal entry: it can be edited, merged by hand, or deleted.
- Conflict copies are tagged (`title` suffix plus a small badge in lists) and appear in a "Needs attention" section in the sidebar until opened.

Both platforms produce the same result: the web adapter creates the copy itself after a 409 (§3.3); the desktop engine creates it during push (§8.4).

## 10. Visual design

- **Feel:** quiet and paper-like, focused on writing. The editor column is limited to about 68 characters per line, with generous line height.
- **Type:** a readable serif for entry text (for example "Source Serif 4"), a clean sans for UI chrome. Fonts are bundled in the app, never loaded from a CDN, so the desktop app works offline and the CSP stays `'self'`.
- **Theme:** light, dark and system. Tailwind with CSS variables as tokens; the `@tailwindcss/typography` plugin styles editor content.
- **Calendar:** days with entries get a dot whose size reflects word count, giving a sense of writing rhythm across the month.
- **Motion:** minimal; respects `prefers-reduced-motion`.

## 14. How later stages plug in

| Later stage | Frontend change | What stays |
|---|---|---|
| **L1 Live typing (Yjs)** | Add TipTap's `Collaboration` extension and a Yjs provider that speaks to `/v1/docs/{id}` over WebSocket. The editor binds to a `Y.Doc` instead of JSON + autosave. Desktop persists Yjs state in SQLite (a `doc_state` blob per entry) and syncs updates through the same Go engine. Conflict copies and §9 go away for bodies. A one-time step converts each entry's ProseMirror JSON to a `Y.Doc` (`prosemirrorJSONToYDoc`). | Screens, routing, adapter pattern, calendar, search UI |
| **L2 End-to-end encryption** | Passphrase entry on first run; key derived with Argon2 (WASM) and kept in the keychain (desktop) or memory (web). Bodies encrypted before `saveEntry`; search runs only on local data (desktop) or a client-side index (web). | Sync engine, outbox, conflict rules |
| **L3 Sharing** | Share dialog, member list, presence avatars and remote cursors (Yjs awareness). | Everything else |
| **L4 Scale** | No frontend change; the server URL and API stay the same. | All of it |
