## 1. Responsibilities

The server is the **single source of truth** for diary entries. It:

- Stores every entry and assigns each change a position in a per-user change log (`server_seq`).
- Accepts writes only when they are based on the latest version (optimistic concurrency).
- Tells connected clients that something changed (SSE), and serves the changes on request (`/v1/sync`).
- Identifies the owner (Tailscale identity or a password).
- Serves the built web UI from the same binary and origin.
- Backs itself up.

It does **not**: render HTML from entries, merge text, or keep any important state in memory. Everything that matters is in SQLite; memory holds only open SSE connections.

## 2. Architecture and package layout

The server follows **ports and adapters** (hexagonal architecture). The core logic depends only on interfaces. Concrete technology (SQLite, HTTP, Tailscale) lives in adapters at the edge.

```
            ┌──────────────────────── adapters (edge) ─────────────────────────┐
 HTTP ───►  │ httpapi: routing, JSON, SSE, middleware                          │
            │      │                                                           │
            │      ▼                                                           │
            │ ┌──────────── core ─────────────┐                                │
            │ │ EntryService, SyncService     │── uses ──► ports (interfaces)  │
            │ │ (rules: versions, conflicts)  │            Store, Notifier,    │
            │ └───────────────────────────────┘            Authenticator, Clock│
            │                                                   ▲              │
            │ sqlitestore · memnotifier · auth/tailscale · auth/password       │
            └──────────────────────────────────────────────────────────────────┘
```

**Dependency rule:** `core` imports nothing from `adapters` or `httpapi`. Adapters import `core`. `main.go` is the only place that knows every concrete type.


## 3. Configuration

All configuration comes from environment variables, parsed once at startup into a `Config` struct. Invalid combinations fail fast with a clear message.

| Variable | Default | Meaning |
|---|---|---|
| `DIARY_ADDR` | `127.0.0.1:8080` | Listen address |
| `DIARY_DATA_DIR` | `/data` | Directory for `diary.db` and `backups/` |
| `DIARY_DB` | `sqlite` | Store adapter (`postgres` later) |
| `DIARY_NOTIFY` | `memory` | Notifier adapter (`redis` later) |
| `DIARY_AUTH_MODE` | `tailscale` | `tailscale` or `password` |
| `DIARY_OWNER_LOGIN` | _required in tailscale mode_ | Tailscale login allowed in, e.g. `you@github` |
| `DIARY_PASSWORD_HASH` | _required in password mode_ | argon2id PHC string |
| `DIARY_TOKEN_SECRET` | _required in password mode_ | 32+ random bytes, base64, signs tokens |
| `DIARY_BACKUP_KEEP` | `14` | Number of nightly backups to keep |
| `DIARY_LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `DIARY_MAX_ENTRY_BYTES` | `2097152` | Request body limit for one entry (2 MB) |

Validation examples:
- `DIARY_AUTH_MODE=password` without `DIARY_PASSWORD_HASH` → exit with `DIARY_PASSWORD_HASH is required when DIARY_AUTH_MODE=password`.
- `DIARY_AUTH_MODE=tailscale` with `DIARY_ADDR` not on `127.0.0.1` → exit. Identity headers are only trustworthy if nothing but the Tailscale sidecar can reach the server (see §11).

A helper subcommand creates the password hash so users never handle argon2 parameters by hand:

```
docker compose run --rm diary hash-password
```

## 4. Startup and shutdown

```go
func main() {
    cfg := config.MustLoad()
    log := newLogger(cfg.LogLevel)

    store, err := sqlitestore.Open(filepath.Join(cfg.DataDir, "diary.db"))
    must(err)
    must(store.Migrate(ctx))                 // goose, embedded migrations

    notifier := memnotifier.New()
    auth := pickAuth(cfg)                     // tailscale | password
    clock := core.SystemClock{}

    entries := core.NewEntryService(store, notifier, clock)
    syncs := core.NewSyncService(store)

    handler := httpapi.New(httpapi.Deps{
        Entries: entries, Sync: syncs, Notifier: notifier,
        Auth: auth, Log: log, MaxEntryBytes: cfg.MaxEntryBytes,
        WebUI: webui.FS(),
    })

    srv := &http.Server{
        Addr:              cfg.Addr,
        Handler:           handler,
        ReadHeaderTimeout: 10 * time.Second,
        ReadTimeout:       30 * time.Second,
        WriteTimeout:      30 * time.Second, // SSE route lifts this per request
        IdleTimeout:       120 * time.Second,
    }

    go backup.Nightly(ctx, store, cfg.DataDir, cfg.BackupKeep, log)
    go store.CleanupLoop(ctx)                 // expire old idempotency rows

    // graceful shutdown on SIGINT/SIGTERM
    go func() { <-ctx.Done(); notifier.CloseAll(); srv.Shutdown(context.Background()) }()
    log.Info("listening", "addr", cfg.Addr, "auth", cfg.AuthMode)
    if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) { log.Error("server", "err", err) }
    store.Close()
}
```

On `SIGTERM` (Docker stop): close all SSE streams first, so clients reconnect promptly to the new container, then drain in-flight requests, then close the database cleanly.

## 5. Domain model

```go
// shared/model/entry.go
type Entry struct {
    ID        string     `json:"id"`         // UUID v7, generated by the client
    EntryDate *string    `json:"entry_date"` // "2026-10-05" or null for free notes
    Title     string     `json:"title"`
    Body      json.RawMessage `json:"body"`  // ProseMirror JSON document
    Version   int        `json:"version"`    // 1 on create, +1 every write
    ServerSeq int64      `json:"server_seq"`
    CreatedAt time.Time  `json:"created_at"`
    UpdatedAt time.Time  `json:"updated_at"`
    DeletedAt *time.Time `json:"deleted_at"` // non-nil = tombstone
}
```

**Why these fields**
- **`ID` from the client (UUID v7):** an entry created offline already has its permanent ID, so the outbox can reference it before the server has seen it. v7 UUIDs are time-ordered, which keeps index inserts efficient.
- **`EntryDate`:** a diary is organised by day. The date is the user's local calendar date, chosen by the client, never derived from a server timestamp (a late-night entry in UTC+10 must not land on the wrong day).
- **`Version`:** used only for conflict detection on a single entry.
- **`ServerSeq`:** used only for sync ordering across all of a user's entries. It is assigned by the server so it is immune to clock differences between devices.
- **`DeletedAt`:** deletes become tombstones so other devices learn about them through `/v1/sync`.

`body_text` (plain text for search) is **not** sent by clients. The server derives it from `Body` with `shared/prosemirror.ExtractText`, so it can never disagree with the real content.

Core errors:

```go
var (
    ErrNotFound            = errors.New("not found")
    ErrConflict            = errors.New("version conflict")     // carries current entry
    ErrIdempotencyMismatch = errors.New("idempotency key reused with a different request")
    ErrResyncRequired      = errors.New("cursor too old")       // reserved, see §8.6
)

type ConflictError struct{ Current model.Entry }
func (e *ConflictError) Error() string { return "version conflict" }
func (e *ConflictError) Unwrap() error { return ErrConflict }
```

## 6. Ports (interfaces)

```go
// server/internal/core/ports.go
type Store interface {
    GetEntry(ctx context.Context, userID, id string) (model.Entry, error)
    PutEntry(ctx context.Context, userID string, in PutInput) (model.Entry, error)
    DeleteEntry(ctx context.Context, userID string, in DeleteInput) (model.Entry, error)
    ChangesSince(ctx context.Context, userID string, cursor int64, limit int) (ChangePage, error)
    ListByDate(ctx context.Context, userID, from, to string) ([]model.Entry, error)
    Search(ctx context.Context, userID, query string, limit int) ([]SearchHit, error)
    EnsureUser(ctx context.Context, login string) (userID string, err error)
}

type PutInput struct {
    ID, IdemKey  string
    BaseVersion  int           // 0 = create
    EntryDate    *string
    Title        string
    Body         json.RawMessage
    BodyText     string
    RequestHash  [32]byte      // sha256 of the request body, for idempotency checks
}

type ChangePage struct {
    Changes []model.Entry
    Cursor  int64   // pass back as ?since=
    HasMore bool
}

type Notifier interface {
    Publish(ctx context.Context, userID string, cursor int64) error
    Subscribe(ctx context.Context, userID string) (updates <-chan int64, cancel func())
    CloseAll()
}

type Authenticator interface {
    // Identify returns the stable login for this request, or ErrUnauthenticated.
    Identify(r *http.Request) (login string, err error)
}

type Clock interface{ Now() time.Time }
```

Keeping `Clock` as a port makes timestamps deterministic in tests.

## 7. SQLite store in depth

### 7.1 Connections

SQLite allows many readers but only **one writer at a time**. The adapter opens two `*sql.DB` pools on the same file:

```go
const pragmas = "_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)" +
                "&_pragma=foreign_keys(1)&_pragma=synchronous(NORMAL)"

writer, _ := sql.Open("sqlite", "file:"+path+"?"+pragmas+"&_txlock=immediate")
writer.SetMaxOpenConns(1)              // serialise writes in Go, not via SQLITE_BUSY

reader, _ := sql.Open("sqlite", "file:"+path+"?"+pragmas+"&mode=ro")
reader.SetMaxOpenConns(4)
```

- **WAL** lets reads continue while a write is in progress.
- **`_txlock=immediate`** takes the write lock at `BEGIN`, which avoids the classic "upgrade from read to write lock" deadlock.
- **`synchronous(NORMAL)`** is safe in WAL mode and much faster; at worst the last transaction is lost on power failure, never corruption.
- Driver: `modernc.org/sqlite` (pure Go), so the binary builds with `CGO_ENABLED=0` and runs on a distroless image.

### 7.2 Schema

Migrations live in `server/migrations/` and are embedded into the binary; `goose` applies them at startup.

```sql
-- 0001_init.sql
CREATE TABLE users (
  id          TEXT PRIMARY KEY,
  login       TEXT NOT NULL UNIQUE,
  created_at  TEXT NOT NULL
);

CREATE TABLE entries (
  id          TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL REFERENCES users(id),
  entry_date  TEXT,
  title       TEXT NOT NULL DEFAULT '',
  body        TEXT NOT NULL DEFAULT '{"type":"doc","content":[]}',
  body_text   TEXT NOT NULL DEFAULT '',
  version     INTEGER NOT NULL,
  server_seq  INTEGER NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  deleted_at  TEXT
);
CREATE UNIQUE INDEX entries_sync ON entries(user_id, server_seq);
CREATE INDEX entries_date        ON entries(user_id, entry_date) WHERE deleted_at IS NULL;

CREATE TABLE seq_counters (
  user_id   TEXT PRIMARY KEY REFERENCES users(id),
  last_seq  INTEGER NOT NULL
);

CREATE TABLE idempotency (
  user_id       TEXT NOT NULL,
  key           TEXT NOT NULL,
  request_hash  BLOB NOT NULL,
  status        INTEGER NOT NULL,
  response      BLOB NOT NULL,
  created_at    TEXT NOT NULL,
  PRIMARY KEY (user_id, key)
);

-- Full-text search. External-content table: stores only the index, reads text from entries.
CREATE VIRTUAL TABLE entries_fts USING fts5(
  title, body_text, content='entries', content_rowid='rowid', tokenize='porter unicode61'
);
CREATE TRIGGER entries_ai AFTER INSERT ON entries BEGIN
  INSERT INTO entries_fts(rowid, title, body_text) VALUES (new.rowid, new.title, new.body_text);
END;
CREATE TRIGGER entries_ad AFTER DELETE ON entries BEGIN
  INSERT INTO entries_fts(entries_fts, rowid, title, body_text) VALUES ('delete', old.rowid, old.title, old.body_text);
END;
CREATE TRIGGER entries_au AFTER UPDATE ON entries BEGIN
  INSERT INTO entries_fts(entries_fts, rowid, title, body_text) VALUES ('delete', old.rowid, old.title, old.body_text);
  INSERT INTO entries_fts(rowid, title, body_text) VALUES (new.rowid, new.title, new.body_text);
END;
```

Timestamps are stored as RFC 3339 UTC text, which sorts correctly and is readable when inspecting the file.

### 7.3 Writing an entry (`PutEntry`), step by step

Everything below runs in **one transaction**. The notifier is called only **after** commit.

```
BEGIN IMMEDIATE
 1. Idempotency check
      SELECT request_hash, status, response FROM idempotency WHERE user_id=? AND key=?
      ├─ found, same hash      → ROLLBACK, return the stored response (the retry is harmless)
      ├─ found, different hash → ROLLBACK, ErrIdempotencyMismatch (422)
      └─ not found             → continue
 2. Load current state
      SELECT version, deleted_at FROM entries WHERE id=? AND user_id=?
 3. Decide
      ├─ no row,  base_version = 0  → create (version 1)
      ├─ no row,  base_version > 0  → ErrNotFound (404)
      ├─ row,     version ≠ base    → ConflictError{Current} (409)
      └─ row,     version = base    → update (version + 1, clears deleted_at)
 4. Next sequence number (works unchanged on Postgres)
      INSERT INTO seq_counters(user_id, last_seq) VALUES(?, 1)
      ON CONFLICT(user_id) DO UPDATE SET last_seq = last_seq + 1
      RETURNING last_seq
 5. Write the row
      INSERT ... or UPDATE entries SET title=?, body=?, body_text=?, entry_date=?,
             version=version+1, server_seq=?, updated_at=?, deleted_at=NULL
      WHERE id=? AND user_id=? AND version=?        -- guard repeated in SQL
 6. Store the idempotency record (status 200 + JSON of the saved entry)
COMMIT
 7. notifier.Publish(userID, server_seq)
```

**Why the version is checked twice** (step 3 in Go, step 5 in `WHERE version=?`): the Go check produces a good error with the current entry; the SQL guard makes the rule impossible to break even if a future code path forgets step 3.

**Why conflicts are not stored in the idempotency table:** a 409 depends on the state at that moment. If the client retries the same request after resolving, it uses a new key anyway.

### 7.4 Deleting an entry

Same transaction shape as `PutEntry`, with step 5 replaced by:

```sql
UPDATE entries
SET deleted_at = ?, title = '', body = '{"type":"doc","content":[]}', body_text = '',
    version = version + 1, server_seq = ?, updated_at = ?
WHERE id = ? AND user_id = ? AND version = ?
```

The content is wiped on delete, because a diary's deleted text should not linger in the database. The row (id, version, seq, deleted_at) stays as a tombstone so every device learns about the delete.

### 7.5 Reading changes (`ChangesSince`)

```sql
SELECT * FROM entries
WHERE user_id = ? AND server_seq > ?
ORDER BY server_seq
LIMIT ? + 1          -- fetch one extra row to know if there is more
```

- If `limit + 1` rows come back: return the first `limit`, `HasMore = true`.
- `Cursor` = `server_seq` of the last returned row, or the input cursor if nothing changed.
- Because every write gets a new, higher `server_seq`, an entry edited five times appears **once**, at its latest position. Clients never replay history; they receive current state.

### 7.6 Search

```sql
SELECT e.id, e.title, e.entry_date,
       snippet(entries_fts, 1, '[', ']', '…', 12) AS snippet
FROM entries_fts
JOIN entries e ON e.rowid = entries_fts.rowid
WHERE entries_fts MATCH ? AND e.user_id = ? AND e.deleted_at IS NULL
ORDER BY rank
LIMIT ?
```

User input is converted to a safe FTS5 query (each word quoted, prefix `*` on the last word) so characters like `"` or `-` never cause syntax errors. The snippet markers are plain characters; the UI turns them into highlights, so no HTML is ever produced by the server.

### 7.7 Housekeeping

- `CleanupLoop` deletes idempotency rows older than 7 days, once an hour.
- `PRAGMA optimize` runs on shutdown and daily.
- `PRAGMA wal_checkpoint(TRUNCATE)` runs after the nightly backup to keep the WAL file small.

## 8. Sync protocol in depth

### 8.1 Concepts

| Term | Meaning |
|---|---|
| **Version** | Per-entry counter. Answers "is my edit based on the latest copy of this entry?" |
| **server_seq** | Per-user counter across all entries. Answers "what changed since I last looked?" |
| **Cursor** | The highest `server_seq` a client has applied. Stored by each client. |
| **Tombstone** | An entry with `deleted_at` set. Sync delivers it like any other change. |
| **Idempotency key** | A UUID per write attempt. Makes retries safe. |

### 8.2 Pull: `GET /v1/sync?since=1842&limit=500`

```json
200 OK
{
  "changes": [
    {
      "id": "0192a3c4-7b1e-7c2a-9f00-1a2b3c4d5e6f",
      "entry_date": "2026-10-05",
      "title": "Monday",
      "body": {"type":"doc","content":[{"type":"paragraph","content":[{"type":"text","text":"Long day..."}]}]},
      "version": 8,
      "server_seq": 1843,
      "created_at": "2026-10-05T07:12:00Z",
      "updated_at": "2026-10-05T21:40:13Z",
      "deleted_at": null
    }
  ],
  "cursor": 1843,
  "has_more": false
}
```

Clients loop while `has_more` is true. A brand new device starts with `since=0` and pages through everything.

### 8.3 Push: `PUT /v1/entries/{id}`

```
PUT /v1/entries/0192a3c4-...
Idempotency-Key: 7f9e1c2d-...
Content-Type: application/json

{ "base_version": 7, "entry_date": "2026-10-05", "title": "Monday", "body": { ... } }
```

| Result | Status | Body |
|---|---|---|
| Saved | `200` | the saved entry (new `version`, `server_seq`) |
| Someone else saved first | `409` | `{"error":"conflict","current": <entry>}` |
| `base_version > 0` but entry unknown | `404` | `{"error":"not_found"}` |
| Same idempotency key, different body | `422` | `{"error":"idempotency_mismatch"}` |
| Body too large / invalid JSON | `413` / `400` | `{"error":"..."}` |

### 8.4 Delete: `DELETE /v1/entries/{id}?base_version=8`

Same status codes. Returns the tombstone.

### 8.5 Walkthrough: two devices, one conflict

```
seq/ver   Laptop (offline)              Server                    Browser
          edits "Monday" (base v7)       v7, seq 1842
                                         ◄── PUT base 7 ────────── edits "Monday"
                                         v8, seq 1843  ── 200 ───►
          back online
          PUT base 7 ──────────────────► version 8 ≠ 7
          ◄── 409 current=v8 ───────────
          keep v8 as "Monday"
          new id: "Monday (conflict copy)"
          PUT base 0 ──────────────────► v1, seq 1844  ── SSE ───► pulls, sees the copy
```

Nobody's text is lost, and both devices end with the same two entries.

### 8.6 Edge cases and their rules

| Case | Rule |
|---|---|
| Client retries a PUT whose response was lost | Same idempotency key → stored response returned, no double write |
| PUT to a tombstoned entry with matching base | Restores the entry (undelete) |
| PUT to a tombstoned entry with old base | 409 with the tombstone as `current`; client offers to restore its text as a new entry |
| Two tabs of the web UI on the same entry | Treated like two devices; the slower save gets 409 |
| Client cursor ahead of server (server restored from an old backup) | Server returns `409 {"error":"cursor_ahead"}`; client resets cursor to 0 and re-pulls; local unsent edits stay in its outbox |
| Tombstone purging | Not done in v1 (tombstones are tiny). If added later, cursors older than the purge horizon get `410 resync_required` |

## 9. Live notices: notifier and SSE

### 9.1 What is sent

Only "the cursor moved". Never entry content. Clients respond by calling `/v1/sync`. This keeps the live channel simple and makes missed messages harmless.

```
retry: 3000

id: 1843
event: changed
data: {"cursor":1843}

: ping
```

### 9.2 In-memory notifier

```go
// server/internal/adapters/memnotifier/notifier.go
type Notifier struct {
    mu   sync.Mutex
    subs map[string]map[*sub]struct{}   // userID → subscribers
}
type sub struct{ ch chan int64 }

func (n *Notifier) Subscribe(_ context.Context, userID string) (<-chan int64, func()) {
    s := &sub{ch: make(chan int64, 1)}
    n.mu.Lock()
    if n.subs[userID] == nil { n.subs[userID] = map[*sub]struct{}{} }
    n.subs[userID][s] = struct{}{}
    n.mu.Unlock()
    return s.ch, func() {
        n.mu.Lock(); delete(n.subs[userID], s); n.mu.Unlock()
    }
}

func (n *Notifier) Publish(_ context.Context, userID string, cursor int64) error {
    n.mu.Lock(); defer n.mu.Unlock()
    for s := range n.subs[userID] {
        select {
        case s.ch <- cursor:
        default: // buffer full: replace the stale value, only the latest cursor matters
            select { case <-s.ch: default: }
            s.ch <- cursor
        }
    }
    return nil
}
```

The buffer of 1 with "latest wins" means a slow client can never block a write and never builds up a backlog.

### 9.3 SSE handler

```go
func (h *Handler) events(w http.ResponseWriter, r *http.Request) {
    userID := userFrom(r.Context())
    rc := http.NewResponseController(w)
    _ = rc.SetWriteDeadline(time.Time{})          // no write timeout on this stream

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("X-Accel-Buffering", "no")

    updates, cancel := h.notifier.Subscribe(r.Context(), userID)
    defer cancel()

    fmt.Fprint(w, "retry: 3000\n\n")
    rc.Flush()

    ping := time.NewTicker(25 * time.Second)       // keeps proxies from closing idle streams
    defer ping.Stop()
    for {
        select {
        case <-r.Context().Done():
            return
        case c, ok := <-updates:
            if !ok { return }
            fmt.Fprintf(w, "id: %d\nevent: changed\ndata: {\"cursor\":%d}\n\n", c, c)
            rc.Flush()
        case <-ping.C:
            fmt.Fprint(w, ": ping\n\n")
            rc.Flush()
        }
    }
}
```

On reconnect, browsers send `Last-Event-ID`. The server does not need to replay anything: the client's next `/v1/sync` call catches up from its own cursor.

## 10. HTTP layer

### 10.1 Routes

Go 1.22+ `http.ServeMux` patterns are enough; no router library is needed.

```go
mux.HandleFunc("GET    /v1/health",        h.health)          // no auth
mux.HandleFunc("POST   /v1/auth/login",    h.login)           // password mode only
mux.HandleFunc("GET    /v1/me",            h.me)
mux.HandleFunc("GET    /v1/sync",          h.sync)
mux.HandleFunc("PUT    /v1/entries/{id}",  h.putEntry)
mux.HandleFunc("DELETE /v1/entries/{id}",  h.deleteEntry)
mux.HandleFunc("GET    /v1/entries/{id}",  h.getEntry)
mux.HandleFunc("GET    /v1/entries",       h.listEntries)     // ?from=2026-10-01&to=2026-10-31
mux.HandleFunc("GET    /v1/search",        h.search)          // ?q=
mux.HandleFunc("GET    /v1/events",        h.events)
mux.Handle("/", webui.Handler())                              // everything else: the web app
```

### 10.2 Middleware chain (outermost first)

1. **Recover:** a panic becomes a logged 500, never a crashed process.
2. **Request ID:** generate or accept `X-Request-ID`, put it in the context and response.
3. **Access log:** method, path, status, duration, request ID (`log/slog`).
4. **Security headers:** see §17.
5. **Auth** (on `/v1/*` except `health` and `login`): resolve login → `EnsureUser` → put `userID` in the context.
6. **CSRF guard** (on `PUT`/`DELETE`/`POST` in password mode): require header `X-Diary-Client: 1`. Browsers cannot send custom headers cross-site without a CORS preflight, which the server never approves.
7. **Body limit:** `http.MaxBytesReader` with `DIARY_MAX_ENTRY_BYTES`.

### 10.3 Error format

Every error response is JSON with a stable machine code and a human message:

```json
{ "error": "conflict", "message": "This entry was changed on another device.", "current": { ... } }
```

| Core error | Status | `error` code |
|---|---|---|
| `ErrUnauthenticated` | 401 | `unauthenticated` |
| `ErrNotFound` | 404 | `not_found` |
| `ConflictError` | 409 | `conflict` |
| `ErrIdempotencyMismatch` | 422 | `idempotency_mismatch` |
| body too large | 413 | `too_large` |
| validation | 400 | `invalid` with `fields` |
| anything else | 500 | `internal` (details only in the log) |

The error codes live in `shared/syncproto` so the desktop client switches on the same constants.

### 10.4 Validation

- `id` must be a valid UUID.
- `entry_date` must match `YYYY-MM-DD` and be a real date.
- `title` ≤ 300 characters.
- `body` must be a JSON object with `"type":"doc"`. Unknown node types are allowed (the editor may gain extensions), but the server never renders them.

## 11. Authentication

### 11.1 Tailscale mode (default)

```
Device on tailnet ──HTTPS──► tailscale sidecar ──HTTP──► diary (127.0.0.1:8080)
                              adds Tailscale-User-Login: you@github
```

- The diary container shares the sidecar's network namespace (`network_mode: service:tailscale`) and listens on `127.0.0.1` only. Nothing except `tailscale serve` can reach it, so the identity header cannot be forged from outside.
- `Identify` reads `Tailscale-User-Login` and compares it to `DIARY_OWNER_LOGIN`. Anyone else on the tailnet (a shared node, a family member) gets 403.
- Requests without the header (for example via Funnel, which does not attach identity) get 401.
- No passwords, no login screen, no cookies needed. The desktop app needs no credentials either, only the server URL, as long as Tailscale runs on the laptop.

### 11.2 Password mode

For setups without Tailscale.

- **Login:** `POST /v1/auth/login {"password": "..."}` → verify against the argon2id hash (`golang.org/x/crypto/argon2`, constant-time compare). Rate limited in memory: 5 attempts per minute per IP, then exponential delay.
- **Token:** on success the server issues a signed token: `base64(payload).base64(HMAC-SHA256(payload, DIARY_TOKEN_SECRET))`, payload = `{login, issued_at, expires_at}`, valid 30 days.
  - **Web:** delivered as a cookie: `HttpOnly; Secure; SameSite=Strict; Path=/`.
  - **Desktop:** returned in the JSON body; stored in the OS keychain; sent as `Authorization: Bearer <token>`.
- **Sign out everywhere:** rotate `DIARY_TOKEN_SECRET`. For a single-user diary, this is simpler than a sessions table and has the same effect.

## 12. Serving the web UI

```go
// server/internal/webui/embed.go
//go:embed all:dist
var dist embed.FS

func Handler() http.Handler {
    sub, _ := fs.Sub(dist, "dist")
    files := http.FileServerFS(sub)
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        p := strings.TrimPrefix(r.URL.Path, "/")
        if _, err := fs.Stat(sub, p); p == "" || err != nil {
            // SPA fallback: unknown paths get index.html so client-side routes work
            w.Header().Set("Cache-Control", "no-cache")
            http.ServeFileFS(w, r, sub, "index.html")
            return
        }
        if strings.HasPrefix(p, "assets/") { // Vite adds content hashes to these names
            w.Header().Set("Cache-Control", "public, max-age=31536000, immutable")
        }
        files.ServeHTTP(w, r)
    })
}
```

- `index.html` is never cached, so a deploy is picked up on the next page load.
- Hashed assets are cached forever, because a new build produces new file names.
- `/v1/*` routes are registered first and never fall through to the SPA.
- During development, `dist/` contains a placeholder `index.html` so `go build` works before the UI exists.

### 13.3 Upgrades

`docker compose pull && make up`. Migrations run at startup inside a transaction; if one fails, the server refuses to start and the previous database file is untouched. The nightly backup (§14) is the second safety net.

## 14. Backups and data safety

- **Nightly:** at 03:00 local time, `VACUUM INTO '/data/backups/diary-2026-10-05.db'` produces a consistent, compacted copy without stopping the server. The oldest files beyond `DIARY_BACKUP_KEEP` are deleted.
- **Before migrations:** the same `VACUUM INTO` runs before any pending migration is applied (`diary-pre-0003.db`).
- **Off-machine (optional):** mount the backups folder somewhere synced, or add Litestream as another compose service to stream the WAL to S3-compatible storage.
- **Export:** `GET /v1/export` (M5) returns a zip of Markdown files, one per entry, so your diary is never locked into this app.
- **Restore:** stop the stack, copy a backup over `/data/diary.db`, start. Clients detect `cursor_ahead` (§8.6) and re-pull automatically.

## 15. Logging and health

- `log/slog` with a JSON handler; one line per request plus important events (startup config summary without secrets, migrations, backups, auth failures).
- Entry content and titles are **never** logged.
- `GET /v1/health` returns `{"status":"ok","db":"ok","version":"1.0.0"}` after a `SELECT 1` on the reader pool.
- `diary healthcheck` (the Docker healthcheck) calls `/v1/health` on the configured address and exits 0 or 1. This avoids needing `curl` in a distroless image.

## 16. Testing strategy

| Level | What | How |
|---|---|---|
| Unit | core services: version rules, conflict errors, validation | fake `Store` + fake `Clock` |
| Contract | every `Store` adapter behaves the same | one suite (`storetest.Run(t, open)`) run against SQLite now, Postgres later |
| HTTP | status codes, JSON shapes, auth, CSRF header, body limits | `httptest.Server` with real SQLite in a temp dir |
| Sync scenarios | multi-device stories end to end | two fake clients against one test server: offline edits, conflict, delete vs edit, lost response + retry, restore from backup |
| SSE | notice arrives after commit, slow client does not block writes | subscribe, publish 1,000 times, assert latest cursor received |

Store contract cases (minimum):
1. Create with `base_version=0` returns version 1 and a `server_seq`.
2. Update with the correct base increments version; wrong base returns `ConflictError` with the current entry.
3. Each write gets a strictly increasing `server_seq`.
4. `ChangesSince` returns each entry once, at its latest state, paginates correctly.
5. Delete produces a tombstone with wiped content that appears in `ChangesSince`.
6. Same idempotency key + same body returns the original result; different body returns `ErrIdempotencyMismatch`.
7. One user can never read or write another user's entries.
8. Search finds words in titles and bodies and excludes tombstones.

## 17. Security checklist

- [ ] Server reachable only through the Tailscale sidecar, or on host loopback in `off` mode.
- [ ] Identity header trusted only because the listener is on `127.0.0.1` inside the sidecar's namespace.
- [ ] Owner allowlist (`DIARY_OWNER_LOGIN`) checked on every request.
- [ ] argon2id password hashing, constant-time comparison, login rate limit.
- [ ] Cookies: `HttpOnly; Secure; SameSite=Strict`.
- [ ] CSRF: custom header required on writes; no CORS headers emitted at all.
- [ ] Response headers on every request:
  ```
  Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'
  X-Content-Type-Options: nosniff
  Referrer-Policy: no-referrer
  Permissions-Policy: camera=(), microphone=(), geolocation=()
  ```
- [ ] The server never renders entry content as HTML; the editor renders ProseMirror JSON through its schema, which drops unknown markup.
- [ ] Request body limits; JSON decoding with `DisallowUnknownFields` on request types.
- [ ] No entry content in logs.
- [ ] Container runs as non-root on a distroless image; data only in the `/data` volume.

## 18. How later stages plug in

| Later stage | Backend change | What stays untouched |
|---|---|---|
| **L1 Live typing (Yjs)** | New `Relay` port (rooms per entry) and a WebSocket route `/v1/docs/{id}`. New tables `doc_updates(doc_id, seq, blob)` and `doc_snapshots(doc_id, seq, blob)`. The server stores and forwards Yjs updates without parsing them. A one-time migration converts each `body` (ProseMirror JSON) to a Yjs snapshot on the client. `/v1/sync` keeps serving entry metadata (title, date, tombstones). | Auth, entry list, dates, search pipeline shape, Docker setup |
| **L2 End-to-end encryption** | Bodies and Yjs updates arrive encrypted; `body_text` and FTS move to the clients; server stores ciphertext only. | Sync protocol, versions, cursors, tombstones |
| **L3 Sharing** | `doc_members(doc_id, user_id, role)`; every query checks membership instead of only `user_id`; invite and share-link endpoints; multi-user sessions. | Everything keyed by `user_id` already |
| **L4 Scale** | `pgstore` (same SQL via sqlc; `seq_counters` upsert works unchanged), `redisnotifier`/`redisrelay`, Redis sessions, Caddy load balancing, S3 for attachments. Must pass the same contract tests. | Core services, HTTP handlers, both clients |
